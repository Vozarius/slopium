# Бета 16 — фоновый анализ и Spark

## Что изменилось

- Переключение обычных параметров больше не пересоздаёт рендер мира. `AnalysisChanges` отдельно определяет смену источников света, FG и фильтра блоков; только соответствующие подсистемы обновляются. Полная пересборка нужна при смене источников динамического света; повтор одинаковой конфигурации ничего не сбрасывает.
- A–B–B–A: два последовательных замера варианта между непосредственно соседними контролями. Непригодный контроль не пропускается в пользу далёкого подходящего.
- Прогрев 4/6 секунд, измерение 10/15 секунд в обычном/расширенном режимах. Для начальной стабилизации геометрии можно ждать ещё до 10 секунд; если нагрузка постоянная, она фиксируется и сравнивается с контрольной вместо отбрасывания любой пробы с единичной перестройкой.
- Сохраняются посекундные счётчики настоящих кадров, CPU-время render thread и всего процесса, количество/время GC, доли проверок с перестройками, потерей реального фокуса и свёрнутым окном. CPU-время процесса суммирует работу потоков и может превышать длительность пробы.
- Дрейф настоящих FPS между первой и последней половиной полных секунд свыше 15% делает пробу непригодной. У двух повторов и соседних контролей должны совпадать фоновые условия; дрейф контролей ограничен 10%, эффект должен превышать max(5%, дрейф контроля). Это скрининг в текущей сцене, не универсальная гарантия.
- Во время анализа Minecraft.isWindowActive() возвращает true, а noRender от сворачивания подавляется. Реальный фокус ОС не захватывается. После завершения/отмены действует исходный фокус и штатное поведение свёрнутого окна. Настройка pauseOnLostFocus не изменяется.
- Дополнительные профили Spark записываются ПОСЛЕ замеров FPS: до восьми клиентских конфигураций. CPU Java sampler, интервал 10 мс, потоки сгруппированы по имени. Этапы профилирования не участвуют в сравнении FPS. Автоматические фоновые профили других подсистем не контролируются.
- Опциональная интеграция проверена со Spark 1.10.124; используется его клиентский platform и внутренний API. `.sparkprofile` — родной несжатый protobuf, как в Spark, с деревом вызовов и метаданными CLIENT. Spark не включён в JAR Slopium и не требуется для обычного анализа. При несовместимости записывается ошибка профиля.
- Уже запущенную ручную запись Spark анализатор не прерывает: старт анализа блокируется до её завершения.
- В папке отчёта сохраняются JSON, Markdown и `spark/*.sparkprofile`; после полного завершения рядом создаётся ZIP. Автоматических загрузок нет. Статус `profiling` не выдаётся за завершение. При отмене сохраняется частичный отчёт; профили, не начавшиеся до отмены, отсутствуют.

## Ограничения

Нельзя гарантировать идентичное аппаратное планирование свёрнутого и видимого окна: драйвер может применять собственные фоновые лимиты. Другие приложения, тепловой режим, изменяющийся серверный мир и фоновые профилировщики также влияют на результаты. Анализатор фиксирует часть этих условий и сохраняет неопределённый результат при нестабильности; запуск другой игры или тяжёлой GPU-задачи во время анализа ухудшает сравнение.

Spark даёт статистическую картину выполнения CPU, а не полный GPU-профиль. Автоматические диагностические конфигурации включают несколько заведомо затратных функций и кандидатов по высоким FPS; они не объявляются доказанными победителями. Для разбора необходимо передать ZIP с отчётом и профилями.
