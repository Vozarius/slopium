# Slopium

Клиентский мод для **Minecraft 1.21.1 / NeoForge 21.1.242 / Java 21**, версия **Бета 5**. Оптимизации освещения, частиц и визуальной нагрузки Create, экспериментальная генерация кадров. Требуется Sodium 0.8.13 для 1.21.1; меню Reese’s Sodium Options поддерживается.

**Установка:** заменить предыдущий Slopium в клиентской папке mods на `build/libs/slopium-neoforge-1.21.1-beta-5.jar`, перезапустить игру. Серверная установка не нужна. Существующий `config/slopium.json` сохраняется; сбрасывать настройки после обновления не требуется.

## Настройки

Настройки графики → Slopium. В alpha.11 меню организовано по объектам, а не по поколениям экспериментов. Каждый параметр расположен один раз.

| Раздел | Что здесь находится |
|---|---|
| Общее и свет | Общий выключатель, диагностика, трещины, Xaero, оптимизации света и источники Create/Sable |
| Генерация кадров | Выкл / Простая / FSR 3 + Slopium, общий множитель ×2–×32, целевые настоящие FPS, отметка промежуточных кадров, предел выходных FPS, параметры интерполяции |
| Частицы | Скрытие за препятствиями и за радиусом, кеш света, ограничение новых частиц |
| Create: модели и анимации | Скрытие обычных моделей и моделей Flywheel, пауза анимаций за препятствиями или везде, дальние обновления |
| Create: фабричные панели | Радиусы предметов и лампочек, выбор видимости соединений |
| Create: клиентские обновления | Один способ разрежения тиков и только его применимые параметры |
| Предметы и детали мира | Выпавшие предметы, специальные модели блоков, тени, смешивание кадров текстур, фоновые эффекты |

Полные отключения теперь выбираются в соответствующем разделе, без отдельной страницы диагностики. Для моделей и частиц добавлено «Скрыть все», для анимаций — «Приостановить везде», для клиентских тиков — «Заморозить все клиентские тики». Старые полные отключения из JSON отображаются как эти значения.

**Скрывать за препятствиями:** «Выключено» / «За непрозрачными блоками» / «За любыми блоками». Отдельный тумблер больше не нужен. Для частиц в окне выбрать последний вариант; стекло считается препятствием. Неприменимые радиусы и интервалы недоступны; подсказки объясняют зависимость и приоритет полного отключения.

Три прежних способа редких тиков объединены в один выбор. При открытии старой конфигурации показывается фактически приоритетный способ, а выбор нового выключает конкурирующие флаги. EntityCulling доступен как способ только при наличии этого мода. Параметры за препятствиями и за радиусом имеют отдельные подписи.

## Бета 5

В «Генерация кадров» добавлены **«Облегчённые промежуточные кадры»** (экспериментальная опция, выключена по умолчанию). Когда пора показать промежуточное изображение, пропускаются повторная подготовка мира и парные события начала/конца рендера. Камера, прицеливание, рука, интерфейс, тики и ввод продолжают обновляться. Простая генерация сохраняет позднюю геометрию модов в исходном изображении; у FSR эта стадия остаётся отдельной.

При искусственной нагрузке обработчика рендера 12 мс, цели 30 настоящих FPS и ×6 новый путь дал примерно **76 → 137 FPS** для простой генерации и **73 → 128 FPS** для FSR. Вывод включает удержания изображения. Это проверка конкретного вида нагрузки, а не обещание прироста на заводах. [Методика и результаты](docs/BETA5_TESTS.ru.md).

В проверке полного набора модов выигрыш не подтвердился: простая генерация 166 → 147 FPS, FSR 170 → 166 FPS при примерно 30 настоящих FPS. Поэтому функция выключена по умолчанию; включать её стоит только для сравнения в своей сцене.

Новый путь работает в существующем потоке вывода. При полной занятости основного потока или GPU заданный множитель не гарантируется. Если сторонний мод неправильно отображается, выключите только «Облегчённые промежуточные кадры» для сравнения. В `/slopium status` добавлена строка **Frame path**: число коротких/обычных кадров, CPU-время подготовки, рендера и вывода окна. После изменения условий сравнения используйте `/slopium reset`.

## Бета 4

Исправлено искусственное падение настоящих FPS при большом множителе. Настоящая отрисовка запускается по времени, не ожидая обязательных 31 дополнительных кадров при ×32. У простой генерации и FSR общая политика приоритета; у FSR промежуточные позиции выбираются по времени, устаревшие пропускаются. ×32 означает попытку получить **до** 31 дополнительного кадра в свободное время.

«Максимум входных FPS» переименован в **«Целевые настоящие FPS»**. Значение 0 теперь означает **автоматический замер** обычных кадров при включении и каждые 5 секунд (восемь интервалов без генерации), положительные значения 1–240 задают ручную цель. Сохранённые положительные значения используются как цели. В `/slopium status` показаны заданная и рассчитанная частота, настоящие кадры, сгенерированные изображения и удержания отдельно.

Для попытки **30 → 960 FPS**: цель 30, множитель ×32, предел вывода Slopium 0, лимит Minecraft без ограничения и VSync выключен. При пределе 240 FPS снижается фактический множитель, а не обязательно настоящая частота до 240 / 32. Целевая частота и 960 FPS не гарантируются: генерация, HUD и вывод требуют ресурсов. Если настоящий кадр занимает весь доступный интервал, генерация уступает ему время. Автоматический замер тоже может кратковременно снизить суммарный вывод.

Простая генерация сохраняет последнее перепроецированное изображение в дополнительном переиспользуемом GPU-буфере, чтобы удержания не откатывали камеру назад. FSR не запускает подготовку пары, когда отрисовка уже израсходовала интервал с учётом доступной оценки стоимости генерации. Новых потоков и синхронного чтения изображений с GPU нет.

[Проверки Беты 4](docs/BETA4_TESTS.ru.md).

## Бета 3

В разделе **Генерация кадров → Максимум входных FPS** добавлен общий для простой генерации и FSR предел настоящей отрисовки мира: **1–240 FPS**, **0 — без ограничения** (по умолчанию). Например, 60 входных FPS и ×4 задают потолок 240 выходных FPS. Более низкий предел вывода Slopium, лимит Minecraft или VSync ограничат результат дополнительно. Настройка задаёт максимум, а не гарантирует достижение указанной частоты.

Ограничитель использует часы рендера без дополнительных потоков и не меняет частоту серверных тиков. Простая генерация использует перепроекцию, FSR после исчерпания пары удерживает последнее изображение до разрешённого захвата. Повторы считаются отдельно (`held` в `/slopium status`), а не как новые сгенерированные изображения. Резкие повороты камеры также соблюдают предел; первый кадр после смены мира, размеров буфера или настроек захватывается сразу для создания истории. Очень низкий входной FPS ухудшает обновление анимаций и задержку изображения.

[Проверки Беты 3](docs/BETA3_TESTS.ru.md).

## Бета 2

Простая генерация заменена на перепроекцию FrameGen: шейдеры Screamix перенесены с сохранением LGPL-3.0-or-later, проходы адаптированы к управлению ресурсами Slopium. Последний настоящий цвет и глубина переносятся к **текущей камере**, без ожидания следующего настоящего кадра. В этом режиме нет прежнего поиска оптического потока. Сетка перепроекции настраивается отдельно; анимации объектов обновляются на настоящих кадрах. Освещение руки восстанавливается на созданных кадрах.

FSR остаётся настоящим AMD FSR 3.1.6; выше ×2 — гибрид с интерполяцией Slopium. Это алгоритм с задержкой, а не перепроекция FrameGen. GPU-тест теперь проверяет, что FSR переносит движущийся объект между двумя исходными положениями, а не просто возвращает непустое изображение.

Добавлен экранный счётчик: активный алгоритм, настоящие FPS, суммарный вывод и число созданных кадров. Причина блокировки выводится независимо от счётчика, а конфликт с отдельным FrameGen/PFG указан также в подсказке меню. **Отдельный FrameGen/PFG нужно убрать из mods и перезапустить игру**, чтобы проверить генерацию Slopium.

Предел FPS **0 = только лимит Minecraft**. Старые сохранённые пределы не сбрасываются. При проверке включите отметку кадров, поставьте ×2 или ×4, предел Slopium 0, отключите VSync и выберите достаточный лимит Minecraft. При неподвижной камере простая генерация закономерно повторяет изображение. При одинаковом ограничении FPS генерация может сократить настоящую отрисовку, не увеличивая суммарный FPS.

Исходники LGPL-части и лицензии вложены в JAR, полный исходный код с инструкциями сборки — в `slopium-neoforge-1.21.1-beta-2-sources.jar`. Подробности заимствования: [FrameGen-NOTICE.md](licenses/FrameGen-NOTICE.md).

## Бета 1 (история)

Общий ползунок **«Множитель кадров» ×2–×32** работает в обоих режимах. ×N означает N−1 промежуточных кадров и один настоящий. Векторы движения рассчитываются один раз на пару исходных изображений и переиспользуются для всех временных позиций; память не растёт пропорционально множителю.

**FSR выше ×2 — гибридный режим:** AMD FSR 3.1.6 создаёт среднее изображение, Slopium рассчитывает остальные позиции с его использованием. Это не нативный FSR ×32. Параметры интерполяции доступны и для такого режима. Значение по умолчанию осталось ×2.

Для проверки включить **«Помечать сгенерированные кадры»**: розовая полоса сверху появляется только на промежуточных изображениях. `/slopium status` показывает активный множитель и отдельные счётчики. Предел FPS и VSync сохраняются: при лимите 120 и ×32 настоящая отрисовка может опуститься до 3,75 FPS, поэтому большие значения добавляют сильную задержку и артефакты. Для первого сравнения разумно использовать ×4.

В Sodium версия отображается как **«Бета 1»**, файл называется `slopium-neoforge-1.21.1-beta-1.jar`. Служебная версия NeoForge — `1-beta.1`: загрузчик требует, чтобы она начиналась с цифры. Старый префикс `0.1.0` убран из новой версии и имени JAR.

[Подробности и проверки Бета 1](docs/BETA1_TESTS.ru.md).

## Alpha.19 (история)

Два генератора промежуточных кадров: собственная интерполяция с оценкой движения на GPU и настоящий AMD FSR **3.1.6** через нативный мост OpenGL–D3D12. HUD, рука, ввод и игровые тики находятся вне пропуска отрисовки мира. FSR использует общие текстуры в VRAM и GPU-семафоры; изображения не копируются в Java/RAM. По умолчанию генерация выключена.

Настройки → Slopium → **Генерация кадров**. Начальная настройка: «Простая ×2», предел 120, сетка 8, поиск 16, допуск 4. Лимит Minecraft и VSync продолжают действовать: более низкий предел ограничит общий вывод. У FSR отдельный диагностический вид и общий предел FPS; пресеты качества апскейлинга не добавлены, поскольку разрешение не меняется.

Это повышение плавности с дополнительной задержкой и возможными артефактами, а не ускорение серверной логики. FSR требует Windows x64, D3D12 и OpenGL-расширения обмена памятью/семафорами. Shader packs, Fabulous и нестандартные HDR-буферы пока не поддерживаются. При отказе генерации обычная отрисовка сохраняется, причина выводится в чат и `/slopium status`.

[Устройство, проверки и ограничения alpha.19](docs/ALPHA19_TESTS.ru.md). Для сборки исходников теперь нужны CMake, PowerShell 7, Visual Studio C++ и официальный SDK: [native/README.md](native/README.md). Подписанная библиотека AMD включена в JAR со своей лицензией, поэтому размер мода вырос.

## Alpha.18

В «Общее и свет» добавлены два выключенных по умолчанию параметра:

- **Отсекать вне поля зрения камеры** — дополнительная проверка объёмов частиц и обычных моделей Create; для поддержанных Flywheel-визуализаций CPU-пути применяется в его очереди. Результат хранится в той же записи VisibilityPool, что и стены, но обновляется при новой камере. Вне камеры проверка стен не запрашивается. Включённые проверки комбинируются как «внутри камеры И не за препятствием». Штатное отсечение Sodium/Flywheel остаётся независимо от этого тумблера.
- **GPU-куллинг Flywheel за стеклом (тест)** — для «Скрывать модели Flywheel → За любыми блоками» на backend indirect. Копирует основную глубину в отдельную текстуру и дополнительно рисует в неё готовую прозрачную геометрию Sodium. Flywheel использует этот источник для своей пирамиды глубины и существующего GPU-теста камеры/препятствий. Основная глубина и цвет не подменяются, CPU не читает GPU-ответы.

GPU-режим использует реальные поверхности геометрии чанков, включая стекло и воду, но не обещает охват отдельных специальных рендереров. Отверстия остаются открытыми. Это дополнительный проход и расход видеопамяти: прирост FPS не гарантирован. При Iris/Oculus, Fabulous, неподходящем framebuffer или ошибке остаётся CPU-путь. Тики/пауза анимаций остаются CPU-функциями. Переключение состояния Flywheel всё ещё ограничено бюджетом; оно не обязано завершиться за один кадр.

`/slopium status`: `Camera culling`, `GPU glass`, `Flywheel path`. Время GPU glass — время отправки работы на CPU, не время исполнения GPU. [Проверки и ограничения](docs/ALPHA18_TESTS.ru.md).

## Alpha.17

Для «Скрывать модели Flywheel → За непрозрачными блоками» Slopium распознаёт реально созданный `IndirectDrawManager` и оставляет отсечение штатному GPU-пути Flywheel. CPU-очередь моделей Slopium не обходится, если отдельно не нужны анимации. Это использует существующий куллинг Flywheel, а не добавляет новый GPU-проход. Переход возвращает ранее скрытые Slopium экземпляры штатному рендереру; при смене backend возвращается CPU-проверка.

«За любыми блоками» пока сохраняет прежнюю CPU-реализацию с ограниченным набором поддержанных визуализаций. Пауза анимаций и клиентские тики не получают результат из GPU: их независимые CPU-проверки сохранены. GPU-куллинг со стеклом и чтение GPU-видимости для тиков в эту версию не входят.

`/slopium status` показывает `Flywheel path`: наличие штатного GPU-пути и передачу ему непрозрачного режима. `/slopium inspect` поясняет, кто управляет моделями; состояние CPU-записи не является результатом GPU-проверки. Штатное отсечение проверяет объём экземпляра по глубине, поэтому его границы могут отличаться от прежнего луча к центру блока.

[Проверки alpha.17](docs/ALPHA17_TESTS.ru.md).

## Alpha.16

Удешевлена общая таблица видимости: повторно используется проверенное препятствие, изменения геометрии учитываются по колонкам чанков, а проверка только режима «за любыми блоками» заканчивается у первого подходящего препятствия. При запросе непрозрачного режима он вычисляется отдельно, если прежний проход не дал ответа. Для неподвижной камеры периодическая перепроверка выполняется через 20 кадров; обновления блоков ставят проверку в очередь раньше.

Для стандартного запроса света частиц добавлен общий кеш на один кадр, до 4096 позиций. Он работает через существующую настройку кеша света, сохраняет индивидуальные формулы яркости частиц и сбрасывается при смене мира, настроек и обновлении геометрии.

Новых потоков и GPU-проходов нет: уменьшается объём работы внутри прежних ограниченных очередей. В `/slopium status` строка `Visibility reuse` показывает повторное использование путей и препятствий, чтения блоков и попадания в общий кеш света. Это счётчики выполненной работы, не измерение прироста FPS.

[Проверки, результаты и ограничения alpha.16](docs/ALPHA16_TESTS.ru.md).

## Alpha.15

Create и стандартные частицы используют общую таблицу видимости. Один проход по геометрии получает сразу два ответа: «за непрозрачными» и «за любыми». Отрисовка, анимации и тики только запрашивают/читают запись; трассировка выполняется отдельным обработчиком в начале рендера мира. У Create и частиц отдельные очереди и квоты памяти под общим бюджетом 0,75 мс / 512 запросов; применение результатов к Flywheel ограничено отдельно 0,35 мс / 512 операций. Пределы кооперативные, отдельная операция может выйти за время.

Убраны массовое восстановление при каждом движении камеры, выключение скрытия при открытом чате и сброс подтверждённого ответа из-за нехватки бюджета. Это устраняет соответствующие причины мерцания. Последний ответ сохраняется до следующей проверки, поэтому при движении или изменении стены возможна задержка появления/скрытия. Переключение режима и общий выключатель по-прежнему восстанавливают модели. Тесты не заменяют проверку мерцания в пользовательском мире.

`/slopium status`: новая строка `Visibility pool` показывает размер таблицы, очередь, обращения, готовые/неизвестные ответы, лучи и стоимость обработчика. `Culling cost` теперь измеряет применение к Flywheel без трассировки. `/slopium inspect x y z` выводит оба сохранённых ответа и возраст проверки; чат больше не меняет видимость.

[Проверки и ограничения alpha.15](docs/ALPHA15_TESTS.ru.md).

## Alpha.14

Убран полный обход хранилища Flywheel каждый кадр. Визуализации регистрируются при создании и удаляются из индекса вместе с объектами Flywheel. Неподдерживаемые классы распознаются один раз; повторные проверки идут через очередь только для поддерживаемых моделей.

Общий бюджет очереди для менеджеров Flywheel — 0,75 мс и не более 512 операций за кадр, включая регистрацию, проверки и восстановление. Это кооперативный предел: одна операция или пауза JVM может его превысить. Видимые модели перепроверяются через 20 кадров, скрытые/приостановленные — через 8. Во время движения камеры приоритет имеет восстановление, новые скрытия начинаются после двух кадров с неподвижной позицией камеры. Восстановление большого числа моделей может занять несколько кадров.

`/slopium inspect x y z` показывает класс визуализации выбранного механизма, поддержку, последнее решение и первое препятствие для обоих режимов. Без координат проверяется блок под прицелом: при взгляде через окно это обычно само стекло. Команда нужна, чтобы отличить неизвестную визуализацию, статическую геометрию и ошибку проверки препятствия.

Новая строка `Culling queue` показывает размер индекса и количество изменённых моделей. В `Flywheel visibility` счётчик `checked` относится к проверкам очереди, а `registered wrapped/unsupported` — к регистрации объектов, а не обходам каждого кадра. Старые и новые значения этих двух счётчиков напрямую сравнивать нельзя.

[Проверки и ограничения alpha.14](docs/ALPHA14_TESTS.ru.md). Прирост FPS в пользовательском мире пока не измерен. Переработан дорогой обход Flywheel; остальные функции не объявляются автоматически полезными в любой сцене.

## Alpha.13

Исправлено распознавание видимых экземпляров в backend Flywheel Indirect. В Flywheel 1.0.6 публичный InstanceHandleImpl.isVisible() проверяет только состояние AbstractInstancer; живые экземпляры Indirect имеют состояние InstancePage и ошибочно возвращают false. Slopium ранее считал их уже скрытыми и не вызывал setVisible(false). Теперь локальная проверка Slopium распознаёт это конкретное состояние, сохраняя защиту ранее скрытых и удалённых экземпляров. Публичное поведение API Flywheel глобально не меняется.

В `/slopium status` добавлена строка `Culling cost`: среднее и максимальное время прохода Slopium по визуализациям Flywheel, число проходов и суммарное время трассировки Create. Лимит около 1 мс относится только к трассировке, а не ко всему обходу. Это позволяет проверить, окупается ли куллинг в конкретной сцене; итоговый выигрыш требует сравнения времени кадров с режимом и без него.

[Воспроизведение дефекта, тесты и ограничения alpha.13](docs/ALPHA13_TESTS.ru.md).

## Alpha.12

Исправлен пропуск моделей Create, которые Azimuth оборачивает для расширений Bits 'n' Bobs. Slopium теперь получает исходную проверенную визуализацию из обёртки и применяет к ней скрытие и паузу. Владение скрытыми экземплярами привязано к объекту в хранилище Flywheel; замена вращающейся модели при смене материала не возвращает её сквозь стену. Дополнительная геометрия расширений (например цепи BnB) автоматически не скрывается: её границы могут выходить далеко за блок механизма.

Обновления геометрии сбрасывают ответы кеша Create, сохраняя очередь ещё не выполненных проверок. Это предотвращает потерю отложенных запросов при частых обновлениях завода; бюджет трассировки остаётся прежним. В `/slopium status` у Create появились собственные счётчики лучей/кеша и отдельная строка `Flywheel visibility` с числом обработанных, обёрнутых и неподдерживаемых визуализаций.

[Причина ошибки, проверки и ограничения alpha.12](docs/ALPHA12_TESTS.ru.md).

## Alpha.11

Исправлены два пропуска скрытия Create: соседнее окно могло исключаться увеличенной областью модели; большие шестерни не входили в список проверенных визуализаций Flywheel. Теперь проверяется луч к центру блока механизма, исключается только сам целевой блок. Покрытие Flywheel расширено до 11 классов: добавлены большие и закрытые шестерни, ориентированные вращающиеся модели, редукторы, вентиляторы и раздельные валы. Для проверок Create выделен отдельный ограниченный бюджет и очередь.

Пауза теперь охватывает GPU-вращение поддерживаемых деталей: в данные отрисовки записываются нулевая скорость и фиксированный угол, исходные поля Create не меняются. Обновления пресса, миксера и воронки также можно приостановить за препятствием или везде. После отключения паузы используется актуальное состояние механизма. Остальные визуализации и обычный рендер при выключенном Flywheel этим режимом не замораживаются.

Отсечение по центру агрессивное: у края окна могут исчезать частично видимые модели. **Статические корпуса в геометрии чанков не скрываются этими настройками.** Sable-позиции и неизвестная видимость защищены. Серверная симуляция и сетевой протокол не меняются; разрежение клиентских тиков может замедлять звуки, анимации и индикаторы. Пауза вращения сама по себе не гарантирует роста FPS: отрисовка модели остаётся.

[Настройки, тесты и ограничения alpha.11](docs/ALPHA11_TESTS.ru.md). [Журнал проверок](docs/VALIDATION.ru.md).

## Измерения

Включить сбор статистики, выполнить `/slopium reset`, закрыть меню и чат, провести 60–90 секунд в одной сцене, затем `/slopium status`. Сравнивать время кадров и FPS при неизменных позиции, направлении камеры и нагрузке. Строка `Particle visibility` показывает число проверок, скрытий, отложенных запросов и исключений Sable. Счётчики сами по себе не доказывают ускорение.

После применения настроек перестраивается клиентская геометрия и сбрасывается замер кадров: перед сравнением дождаться стабилизации. Полные диагностические отключения нужно выключить при проверке обычных оптимизаций. Distant Horizons и F3 не изменяются.

**60 FPS в заводской сцене и 400 FPS вне заводов не подтверждены.** Для alpha.15 пользовательский FPS ещё не измерен. Предыдущие пользовательские результаты и анализ находятся в `analysis/`.

## Сборка и история

`gradlew.bat build` собирает мод и запускает unit-тесты. Изолированные клиенты: `runSmokeClient -PwithReferenceMods` (full), с `-PsmokeProfile=legacy` (Create без Sable/EntityCulling, старый Create Dynamic Light), с `-PsmokeProfile=minimal` (без Create). Smoke-код не входит в JAR. Эталонные моды используются из `reference/mods` и не встраиваются в Slopium.
