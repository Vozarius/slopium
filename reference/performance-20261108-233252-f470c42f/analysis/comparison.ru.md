# Сравнение диагностик report01 и performance-20261108-233252-f470c42f

## Итог

Основные качественные наблюдения повторились: устойчивых 60 настоящих FPS нет; заметная цена связана с клиентскими тиками и проверками видимости Slopium; параллельная генерация повышает число выводов, последовательная снижает настоящие FPS. Новый Spark подтвердил, где именно тратится время. Точные проценты выигрыша отдельных настроек пока не установлены.

## Сопоставимость

В предыдущем прогоне контрольная медиана — 25.05 FPS, в новом — 25.52 FPS. Диапазоны контрольных проб: 20.18–33.18 и 17.15–30.83 FPS соответственно. Разница медиан около 1.9%, существенного общего улучшения уровня FPS нет.

Почти все исходные настройки совпадают. Различается основной переключатель: раньше Slopium был выключен до старта, теперь включён. Контроль обоих прогонов принудительно включает Slopium, поэтому контрольные конфигурации сопоставимы; вариант original в двух отчётах имеет разный смысл. В новом прогоне original фактически повторяет контроль. Камера также не строго та же: смещение около 2.7 блока, направление примерно на 4° и наклон примерно на 4.4°. Это один район, но не идентичный кадр.

Новый прогон действительно шёл в фоне: около 99.7% проверок без реального фокуса и 89.1% со свёрнутым окном. Всего 232 пробы, 78 контролей, шесть локальных профилей Spark. Полных пересборок, вызванных применением настроек анализатора, всего шесть.

## Ошибка фильтра GC в анализаторе

162 пробы получили предупреждение GC occupied over 10%. В используемых JVM-аргументах включён ZGC. Анализатор суммирует getCollectionTime() всех GC MXBean, включая ZGC Cycles и ZGC Pauses, затем сравнивает сумму с длительностью пробы как будто это остановка приложения. Это некорректно: цикл включает конкурентную работу, пауза учитывается отдельно.

В контрольном Spark-профиле накопленные значения: ZGC Cycles — 620 циклов, средняя длительность около 1394.7 мс; ZGC Pauses — 1860 пауз, средняя длительность около 0.0081 мс. Это накопленная статистика за жизнь JVM, а не измеренные паузы только данного 15-секундного окна. Она не подтверждает, что приложение стояло 2–3 секунды в каждой пробе.

Первичный источник: OpenJDK отдельно накапливает cycle и pause statistics, https://raw.githubusercontent.com/openjdk/jdk21u/master/src/hotspot/share/gc/z/zServiceability.cpp . Анализатору нужно сохранять beans раздельно и использовать паузы/JFR pause events для оценки остановок. Утверждения об огромных stop-the-world паузах по текущему gcMillis делать нельзя.

Автоматическая сводка имеет 63 пригодных пробы из 232. Если убрать только ошибочную отсечку по GC, пригодных по оставшимся базовым условиям будет 198, контролей 65 из 78. Однако при сохранении всех остальных строгих правил по непосредственным контролям, дрейфу и долям фоновой нагрузки доказанных победителей всё равно нет. Пересчёт сохранён отдельно; исходный report.json не изменён.

Дополнительная осторожность: сама оптимизация может менять объём фоновых перестроек. Требование одинаковой доли такой работы способно отбрасывать реальную экономию. Этот показатель нужно разбирать как возможный результат настройки, а не всегда считать внешним вмешательством.

## Общая нагрузка компьютера

Во всех шести профилях Spark сообщает общую CPU-загрузку примерно 96–97%, а нагрузку процесса Minecraft примерно 20–25% по сопоставимым минутным счётчикам. Это указывает на значительную конкуренцию со стороны остальной системы; какие именно процессы её создавали, профиль не устанавливает. Настройки Slopium не могут гарантировать одинаковый доступ к CPU при такой внешней нагрузке.

Физическая память по Spark занята примерно на 84–86%; heap Minecraft ограничен 8 ГБ. Эти показатели не доказывают нехватку heap или необходимость увеличивать Xmx. Поле swap на Windows также нельзя без дополнительной проверки считать фактическим объёмом обращений к файлу подкачки.

## Практический вывод

1. Сначала удешевить ветку CreateWallControl.skipTick и общий доступ к видимости: решение должно читаться из дешёвого кеша, без повторной подготовки на каждый тик каждого блока. Эта цель теперь подтверждена деревьями вызовов.
2. Согласовать GPU-путь Flywheel с фильтром блоков, чтобы выбранный режим действительно применялся.
3. Исправить учёт ZGC и причинную трактовку фоновых перестроек в анализаторе. Старый warning GC не означает реальную остановку приложения на указанный процент времени.
4. Проверять исправления короткими адресными A/B без большого перебора и со свободными ресурсами CPU. Полный длительный перебор в текущих условиях не даёт надёжного рейтинга всех переключателей.

Число FPS само по себе не показывает функцию-причину. Здесь профили Spark дали существенно более точную цель, хотя автоматический рейтинг оказался недостаточно надёжен. Изменения исходного кода мода в рамках этого разбора не выполнялись.
