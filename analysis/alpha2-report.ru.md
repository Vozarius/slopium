# Проверка Slopium alpha.2 по профилю 01.09.02

## Вывод

Исправление стоимости проверки тиков сработало: новый профиль показывает **0,82% времени Render thread** в обработчике Slopium вместо **4,19–4,43%** в тяжёлых отрезках alpha.1. Счётчики подтверждают реальный пропуск **1 959 096 тиков**, то есть **17,20% проверок подходящих классов**. Это не равно приросту FPS на 17,20%.

Главная оставшаяся работа — клиентские тики блочных сущностей (**26,01%**) и их рендер (**12,82%**). Дополнительно найдена ошибка прежних версий: обработчик отсечения трещин был внедрён в перегрузку метода, которую обычный рендер мира NeoForge обходит. Исправление вошло в alpha.3 вместе с измерителем времени кадров. Достижение 60 FPS по присланной записи установить нельзя.

## Почему данных EntityCulling недостаточно

В точном JAR `entityculling-neoforge-1.10.5-mc1.21.1.jar` метод `CullTask.cullBlockEntities`:

1. Пропускает типы из исключений и объекты без рендерера блочной сущности.
2. Пропускает принудительно видимые объекты.
3. Выполняет трассировку только при расстоянии **меньше 64 блоков** — в этом методе это константа.

Сохранённый параметр `tracingDistance=128` не заменяет эту проверку 64 в ветке блочных сущностей. Slopium alpha.2 доверяет флагу `isCulled`, поэтому не охватывает все потенциально невидимые механизмы. Ограничение подтверждено кодом, но имеющиеся объединённые счётчики не позволяют определить, какая доля 73,54% объясняется именно им.

Следующий содержательный шаг для тиков — отдельная консервативная проверка выхода за поле зрения для разрешённых классов, с полными границами модели, защитой виртуальных миров/Sable и восстановлением после движения камеры. Её нужно отделить в диагностике от результата трассировки EntityCulling. Простое объявление всех объектов без `isCulled` скрытыми неверно. Увеличение радиуса трассировки само по себе добавляет работу при уже занятом CPU.

## Подтверждённая ошибка отсечения трещин

`culled cracks=0` оказалось недостаточно объяснять ракурсом камеры. В alpha.1/alpha.2 обработчик был внедрён в пятиаргументный `renderBreakingTexture`. NeoForge добавляет перегрузку с шестым аргументом `ModelData`; `LevelRenderer` вызывает её напрямую. В экспортированном фактически преобразованном классе alpha.2 обработчик присутствует только в пятиаргументной перегрузке. Шестиаргументная сразу выполняет исходный рендер.

Это ошибка интеграции Slopium. Запуск меню её не выявлял: метод загрузился, но основной путь не был проверен вызовом. Доказательство сохранено в `alpha2-BlockRenderDispatcher-transformed.javap.txt`.

В alpha.3 указан точный дескриптор перегрузки NeoForge. Старый метод делегирует в неё, поэтому оба пути проходят одну проверку. Проверка Sable выполняется только для кандидатов вне поля зрения. Добавлен счётчик `checked cracks`, позволяющий отличить «нет подходящих невидимых трещин» от отсутствия вызовов.

Тестовый клиент теперь реально вызывает обе перегрузки и проверяет однократное срабатывание обработчика и обход при выключенном Slopium. Тест использует AIR и не воспроизводит геометрию реального мира. Исправление открывает возможность сокращать часть текущих 6,04% на трещины, но **не обещает устранить все 6,04%**: видимые трещины продолжают рисоваться, скрытые за стеной внутри поля зрения пока не отсекаются.

## Время кадров и дальнейшая проверка

При медиане клиентского тика около 16,5–16,9 мс остаётся мало запаса относительно бюджета 16,67 мс на полный кадр при 60 FPS. Тики идут примерно 20 раз в секунду; это не график FPS и не серверный MSPT. В файле нет последовательности времени кадров, позволяющей рассчитать 1% low или проверить минимум 60.

В alpha.3 `/slopium status` добавляет строку `Frames`: средний FPS по длительности интервалов, p50/p95/p99, худший интервал и долю интервалов **дольше 16,67 мс**. Записываются интервалы между началами кадров, включая рендер, ожидания и работу до следующего кадра. Это не GPU-таймер. Сохраняются последние 16 384 интервала; во время записи нет выделений памяти. Сортировка для процентилей происходит только по команде статуса.

Диагностика считает кадры в загруженном мире при закрытых экранах и без паузы. Меню и промежуток до первого кадра после закрытия исключаются. Запись работает и при выключенных оптимизациях Slopium, если включена диагностика. `/slopium reset` и применение настроек сбрасывают замер кадров; применение настроек не сбрасывает остальные счётчики.

После замены alpha.2 на alpha.3 и перезапуска: дождаться завершения загрузки, выполнить `/slopium reset`, закрыть чат, провести минуту в той же сцене, выполнить `/slopium status`. Теперь нужно сохранить **все три строки**. Для проверки именно исправления трещин можно сравнить два замера с выключенным и включённым пунктом отсечения трещин, сохранив остальные параметры. После применения настроек нужно дождаться перестройки чанков и начать новый замер. Общий выключатель Slopium возвращает также штатный свет Create, поэтому такое сравнение не изолирует одну оптимизацию при выключенном свете в конфиге Slopium.

CPU системы в новой записи занят на 94,9–95,3%. Физическая память — 98,57%, свободно примерно 0,46 GiB. Это потенциальный источник нестабильности времени кадров, но профиль не доказывает конкретные задержки подкачки; менять внешнюю нагрузку ради выполнения исходной цели не предлагается.
