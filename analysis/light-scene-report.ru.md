В производной копии для анализа использованы суммы корневых узлов; исходный файл не изменён. Это отмечено в light-scene-summary.json, поле normalization. Первоначальный compare_post_slopium остановился на строгом равенстве: его неполный вывод не используется для выводов.

Категории вложены/пересекаются, их нельзя складывать. Вызовы GL отражают пребывание потока в драйвере, включая возможные ожидания; это не прямой замер GPU. Без GPU-таймингов нельзя объявлять доказанный GPU-bound.

DH остаётся 23,8–27,75% во всех трёх окнах; это не только короткий стартовый всплеск. Его предварительная прогрузка не устраняет рисование каждого кадра. Сохраняется исходное требование пользователя не менять DH.

Конкретные пути вне DH:
- Xaero World Map → TextureUploader.uploadTextures → glFinish: около 2,28% семплов, почти вся стоимость uploadTextures. Это точка исследования синхронизации; просто удалять glFinish без проверки протокола загрузки и повторного использования буферов нельзя.
- ItemEntityRenderer.render: 3,32%; renderMultipleFromCount: 3,10%; кодирование вершин под выпавшими предметами: 2,48%. Кандидат — клиентский LOD числа визуальных копий в стопке, дистанция деталей и проверенное отсечение; не удаление предметов из мира и не изменение их количества.
- F3: 6,82%, включая построение текста и рисование. Кеширование редко меняющихся строк возможно как эксперимент, но нельзя заранее обещать выигрыш всей этой доли. При закрытом F3 эта оптимизация не поможет.
- Рендер AdjustableWheelMountRenderer мода Tracks: 1,16%. Сцена не лишена модовых объектов; нужны мировые границы моделей для радиусного отсечения.
- Flywheel требует отдельного разбора визуальных обновлений и обслуживания буферов, не только draw-вызовов.

Нулевые счётчики тестовых отключений согласуются с текущим конфигом, где все пять отключены. Сам по себе ноль счётчика не доказывает выключенный режим. Старое разрежение скрытых тиков сработало 139 раз; это не главный резерв в этой сцене.

## Условия

Системная загрузка CPU в последних окнах 96,3–97,4%, процесс Java 20,3–32,1%; это не загрузка отдельного ядра. Занято около 87,3% физической памяти. Причину отдельных задержек этими агрегатами доказать нельзя, фоновые нагрузки пользователя сохраняем.

При чтении options.txt: renderDistance=5, simulationDistance=5, VSync=true, maxFps=260. Это текущее состояние файла, а не доказательство настроек в момент записи. В Spark по окнам 145 чанков, но это не прямое значение дальности. Следовательно, профиль не подтверждает целевой сценарий 12 чанков. Лимиты также нужно учитывать перед проверкой цели 400; пользовательские файлы не изменялись.

## Вывод для Slopium

Радиусы Create полезны для заводов, но почти не устранят ограничители этой сцены: все BE-тики здесь около 1%. Приоритеты общего режима — рендер предметов, обновления карты, подготовка Flywheel, дополнительные рендереры и интерфейс. Для отделения CPU и GPU полезен одинаковый короткий замер при меньшем разрешении с прежним DH и той же дистанцией; это диагностический тест, не предложение постоянно снижать качество.

400 FPS при сохранении картинки, DH и системной нагрузки этим профилем не обоснованы. Из него можно выбрать конкретные эксперименты, а не обещать пятикратное ускорение. Отдельные профили показывают две разные проблемы: обслуживание механизмов на заводе и стоимость рендера вне завода. Новая стратегия должна проверять обе, не подменяя их одним общим радиусом.
